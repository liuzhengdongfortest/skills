# 五个操作

两个路径共享，触发即执行。

## 记重点

触发："记一下""记录""存档""存一下"

1. 在 `.boss/meetings/` 下创建 `YYYY-MM-DD-主题/` 目录
2. 生成 notes.md / decisions.md / action-items.md
3. 展示确认后落盘
4. 记的是原始讨论素材，不是正式文档

## 落需求

触发："落盘""落需求""写进requirements""整理成需求"

1. 读取 meetings 中尚未合并的记录，提炼为正式需求文档
2. 写入 `.boss/requirements/`，更新 `VISION.md`
3. **会中决策（落盘前不静默）**：如果改动了已有故事或推翻了旧故事：
   - 扫描 architecture/ 中引用旧故事的设计决策
   - 立刻在会上抛出来："老板，这个改动影响架构决策 A 和 B，兼容性上——旧数据要不要兼容？过渡期两套并存还是直接切？"
   - 老板拍板后，标记旧文档过期，创建 patch 目录，migration.md 直接填入会上已做的决策
   - patch 里不存在待决策项——都是已拍板的

### 用户故事格式

```
### 故事：XXX
**为什么**：（动机、要解决的问题）
**需要什么**：（从用户视角描述需要的能力）
**怎么做**：（实现思路或关键约束，不写伪代码）
```

格式原则：叙事优先、说人话、一个故事一个场景、不写代码和路径、VISION.md 是入口

## 落架构

触发："固化设计""落架构""写进architecture""记录设计"

1. 读取 meetings 中涉及技术设计的记录
2. 提炼为正式架构文档，写入 `.boss/architecture/`，更新 `OVERVIEW.md`
3. 如果设计决策引用了已被 patch 标记过期的需求故事，提醒老板
4. **架构参与度**：根据老板的技术深度自适应——不关心的给默认方案，有判断力的抛选项+tradeoff，深度参与的完整展开（详见路径 A 的「架构参与度」一节）

### 架构文档格式

```
### 决策：XXX
**为了谁**：（服务于哪个需求故事）
**怎么设计**：（结构和协作关系）
**为什么这样**：（理由、替代方案、取舍）
```

格式原则：先讲关系再讲细节、说设计不说实现（同样不写代码和路径）、决策有因、OVERVIEW.md 是入口

## 修补丁

触发："修补丁""处理 patch""看看补丁"

补丁里只有已决策事项，不存在等老板拍板的阻塞问题。修补丁就是执行。

1. 列出 `.boss/patches/` 下所有未关闭的 patch（不在 `_resolved/` 里的）
2. 如果没有指定具体 patch，问老板要先修哪个
3. 逐项执行：确认 migration.md 决策 → 检查 proposals 新草稿 → 正式替换旧文档 → 在 patch.md 中勾掉
4. 全部处理完，patch 目录移入 `patches/_resolved/`
5. 执行中发现新问题，切回路径 A 讨论

## 写代码

触发："实现吧""写代码""改一下XX""把这个故事做了"，或路径 B 中直接讨论代码改动

1. **先读文档，再读代码**：确认需求故事和架构决策，理解当前实现。文档和代码对不上时提醒老板
2. **按架构写**：架构约束是硬杠，不绕着走。发现不合理的切回路径 A 讨论
3. **写完回看文档**：主动问"实现完成了，文档需要更新吗？"
4. **和 patch 联动**：修补丁中写代码就是 patch 执行的一部分，写完勾掉对应项
