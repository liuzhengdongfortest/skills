# 路径 E：计划执行模式

老板给的是长期目标，不是一次性小命令。典型话术：

- "按计划推进"
- "拆 tasks 去做"
- "不要停，做到阶段 X 再汇报"
- "plans 阶段完成以后再来汇报"
- "持续执行这个目标"
- "把最终目标列成 plans"

## 核心判断

长期目标不应该拆成一堆 active plans。正确形态是：

**一个长期目标 = 一个 active 大 plan。**

大 plan 里写完整长期路线，但只细拆当前阶段的待执行条目。规划阶段只在 plan 里列条目，不批量创建 `.boss/tasks/` 文档。助手真正选择某个条目开始执行时，才创建 `.boss/tasks/.../task.md`，并把 plan 中的条目更新为 task 链接或附上 task 链接。

task 是文档，不是一行 markdown 待办。plan 只保留当前阶段条目、已创建 task 的链接、顺序和状态摘要。执行过程中持续细化、改写、删除、重排 task 文档和 plan 索引。阶段完成后，再拆下一阶段条目。

不要提前把未来阶段拆成很多 active plan 文件，那会制造文档堆，不会提高执行力。

## 需求锚点

大 plan 的阶段不是锚点，用户需求才是锚点。

阶段可以变：顺序可以重排，阶段可以合并、拆分、删除，甚至整条路线可以推翻。但这些变化必须能解释为“更好地满足用户需求”。

因此路径 E 的核心不是“按原计划执行”，而是“围绕需求持续校准计划”。

规则：

- 每个 active plan 必须写清楚它服务哪些需求故事或用户目标
- 每个当前阶段待执行条目必须能追溯到需求锚点；真正开工后，需求锚点写入对应 task 文档
- 执行中发现阶段设计错了，可以改阶段；但要在执行记录里说明为什么更贴近需求
- 如果用户需求本身变了，先更新 requirements，再更新 plan/tasks
- 如果 requirements 缺失或太旧，先补需求，不要直接靠 plan 开工
- requirements 只做需求锚点，不承载阶段、任务或执行路线；plan 需要的推进信息写在 plan 里

## 启动门禁

进入路径 E 后，先做六件事：

1. 读 `.boss/CONVENTIONS.md` 和 `.boss/PROFILE.md`
2. 读 `.boss/requirements/VISION.md` 和与目标相关的需求故事
3. 读 `.boss/architecture/OVERVIEW.md` 和与目标相关的架构决策
4. 检查 `.boss/plans/INDEX.md` 和现有 active plan
5. 检查 active plan 是否列出当前阶段待执行条目；`.boss/tasks/INDEX.md` 只索引已经创建且仍活跃的 task 文档
6. 检查 active plan 是否超过 200 行；超过则先压缩

如果没有 active plan，先建一个大 plan。  
如果有多个 active plan，先收敛成一个主 plan，旧计划标 `done`、`paused` 或合并进主 plan。  
如果主 plan 没有当前阶段待执行条目，先在 plan 内拆条目，不要预建 task 文档。
如果需求文档不存在、过旧或与老板当前目标冲突，切回路径 A 先聊清楚，再执行[落需求](operations.md#落需求)。

内部 `update_plan` 只能当临时工作记忆，不能替代 `.boss/plans/`。

## Plan 体积门禁

单个 active plan 不能超过 200 行。

这是硬门槛：

- 读取 active plan 时，如果超过 200 行，先压缩再执行
- 更新 active plan 后，如果超过 200 行，必须在本轮结束前压缩
- 汇报阶段完成前，如果超过 200 行，先压缩再汇报
- 不能用“马上要做完了”绕过 200 行门槛

压缩目标：让 plan 重新变成可操作的工作面板，而不是历史日志。

压缩时保留：

- frontmatter
- 目标
- 需求锚点
- 计划原则
- 总体框架的当前有效版本
- 当前阶段说明
- 当前阶段未完成条目、已创建 task 文档链接和状态摘要
- 完成标准
- 最近 3 条以内关键执行记录；没有新决策时可以不保留执行记录

压缩时删除：

- 已完成阶段总结
- 已完成 task 明细
- 过长验证日志
- 历史决策背景
- 无决策价值的执行流水

旧执行记录可以直接丢弃，因为具体干了什么应该由 `.boss/tasks/` 的活跃任务、归档任务或交付物记录。plan 不是审计日志。

只有当旧记录包含长期有价值、且没有被别处承载的内容时，才转移：

- 产品/领域洞见 → `.boss/wiki/`
- 架构决策 → `.boss/architecture/`
- 任务执行细节 → `.boss/tasks/` 或 `.boss/tasks/_resolved/`

压缩不能改变需求锚点，不能悄悄删除未完成 task，不能丢失重要决策。如果不确定某条旧记录是否重要，问：它是否会影响未来判断？会就沉淀到 wiki/architecture/tasks；不会就删。

## 如何写大 plan

大 plan 必须包含：

```md
---
status: active
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

# 计划：长期目标名

## 目标
最终要达成什么状态，为什么值得做。

## 需求锚点
本 plan 服务哪些需求故事或用户目标。引用 `.boss/requirements/` 路径；如果还没有正式需求，写“待落需求”，并先补需求。

不要为了让 plan 有锚点，把计划内容塞进 requirements。requirements 写“用户为什么需要什么、怎么验收”，plan 写“我们分阶段怎么推进”。

## 计划原则
本计划怎么维护。写明只细拆当前阶段，执行中持续改写。

## 总体框架
阶段 1：...
阶段 2：...
阶段 3：...

## 当前
当前处于哪个阶段，为什么。

## 阶段 N Tasks
- [ ] Task 1：一句话待执行条目 — planned
- [ ] Task 2：一句话待执行条目 — planned
- [ ] [Task 3：已开工条目](../tasks/YYYY-MM-DD-xxx/task.md) — active

## 阶段 N 执行记录
- YYYY-MM-DDTHH:mm:ss+08:00：发现、决策、调整。

## 后续阶段占位
未来阶段暂不细拆，等当前阶段完成后再拆。

## 完成标准
最终目标达成时必须满足哪些可验证条件。
```

## 如何拆当前阶段 tasks

规划阶段先在 active plan 里列当前阶段待执行条目，不要批量创建 task 文档。

task 必须在真正执行时创建为 `.boss/tasks/YYYY-MM-DD-描述/task.md` 文档。active plan 不是 task 本体，只是条目索引和当前状态面板。

一行 markdown checkbox 只能做索引，不能承载 task。原因很简单：task 需要目标、需求锚点、范围、验收、验证、阻塞和执行记录；这些内容塞进 plan 会让 plan 膨胀，也会让任务无法独立归档。

拆 plan 条目的原则：

- 一个条目应该能被一次执行周期推进到可验证结果
- 条目只写标题和一句状态摘要；不要写目标、范围、验收、验证、执行记录
- 条目必须能追溯到需求锚点；如果需求锚点不清楚，先补需求或删掉
- task 文档可以在执行中被拆细、合并、删除或改顺序
- 发现新问题时，更新 task 文档；如果影响阶段排序或状态，再更新当前 plan 的 task 索引
- 不要把未来阶段的 task 提前拆得很细

执行者选择某个条目开工时：

1. 为该条目创建 `.boss/tasks/YYYY-MM-DD-描述/task.md`
2. 把目标、需求锚点、范围、验收、验证写入 task 文档
3. 在 `.boss/tasks/INDEX.md` 增加该活跃 task
4. 把 plan 中对应条目更新为 task 链接或附上 task 链接
5. 再开始执行

task 的执行记录必须用可排序时间戳，而不是只写日期。推荐格式：`YYYY-MM-DDTHH:mm:ss+08:00`。如果同一秒内需要写多条，追加毫秒或序号，如 `2026-05-07T18:42:13.001+08:00`。

task 文档推荐结构：

```md
---
status: pending
created: YYYY-MM-DD
updated: YYYY-MM-DD
plan: ../plans/xxx.md
---

# Task：一句话

## 目标
要推进到什么可验证状态。

## 需求锚点
引用 requirements 或用户目标。

## 范围
本 task 做什么，不做什么。

## 验收
完成时必须看到什么证据。

## 验证
要跑哪些测试、样本、截图、trace 或人工检查。

## 执行记录
- YYYY-MM-DDTHH:mm:ss+08:00：...
```

## 执行循环

如果由 MC Core 常驻拉起 Agent，启动 prompt 必须是进度无关的元指令。

正确写法是要求 Agent 每轮自己重新读取 `.boss/plans/INDEX.md`、唯一 active plan、requirements、architecture 和 tasks，判断当前处于哪个阶段、哪些 task 已完成、下一个最小可验证动作是什么。不要把“当前处于阶段 1”“从 Task 1 开始”“做到某个固定 task”这类进度快照写进常驻 prompt；core 会反复使用同一 prompt，阶段推进后旧快照会污染后续执行。

每轮执行按这个顺序：

1. 读需求锚点，确认当前阶段仍然服务这些需求
2. 读 active plan 的“当前”和当前阶段条目；如果条目已有 task 链接，再打开对应 task 文档
3. 选择下一个最小可验证条目；若还没有 task 文档，先按上面的规则即时创建
4. 在 task 文档的执行记录里用时间戳写一句将要推进什么，以及服务哪个需求；plan 只记录重要状态变化
5. 执行任务
6. 跑实际验证：测试、构建、样本、竞品对比、截图、trace，按任务需要选择
7. 把验证结果和证据路径写回 plan
8. 更新 task 文档状态；完成后归档到 `.boss/tasks/_resolved/YYYY-MM/`，并更新 plan 和 tasks index
9. 如果当前阶段偏离需求，先调整阶段和 tasks，再继续
10. 如果当前阶段 tasks 全部完成，补阶段总结，再拆下一阶段 tasks

默认不要停。能验证的就先验证，能修的就先修；当前 task 卡住，就换同一需求锚点下的其他 task。

## 不停机原则

路径 E 是持续执行模式。老板没有主动问进度、没有明确要求暂停时，不因为单点阻塞而停止整体推进。

遇到这些情况，不要停机：

- 需要老板拍板
- 需求和架构出现冲突
- 当前验证失败且暂时无法自行修复
- 某个实现路径风险越界
- 某个阶段目标已经完成
- 当前上下文不足，不能安全推断

正确动作是：

1. 把阻塞点写入 active plan 的等待区或当前阶段 notes，保持简短
2. 标明：问题、推荐选项、为什么需要老板判断、目前安全边界
3. 不继续推进这个阻塞点
4. 立刻切换到同一长期目标下其他安全有价值的工作

可以切换的工作包括：

- 完善当前阶段其他未阻塞 task
- 优化代码质量、测试、工具链和基础设施
- 补验证、补样本、补竞品对比
- 做竞品调研，记录产品不足
- 清理文档边界、压缩 plan、整理 tasks
- 找风险、补质量门禁、补回归脚本


## 阶段汇报门禁

老板说“阶段 X 完成后再汇报”时，汇报前必须检查：

- active plan 是否不超过 200 行；超过则先压缩
- 阶段 X 是否仍然是满足需求的正确切分；如果中途改过阶段，解释变化
- 阶段 X 的完成是否覆盖了对应需求锚点
- active plan 的阶段 X tasks 是否全部完成或明确转入后续
- 执行记录是否说明做了什么、发现了什么、改了什么
- 验证证据是否存在：测试输出、报告路径、截图、trace、文档之一
- `.boss/plans/INDEX.md` 是否仍只指向正确 active plan

没过门禁，不要说“阶段完成”。

## 和 tasks 目录的关系

`.boss/tasks/` 是状态式任务库。task 是文档，不是一行 checkbox，也不是规划阶段批量生成的占位目录。

使用规则：

- 规划时：只在 plan 里列待执行条目
- 开工时：为被选中的条目创建 `.boss/tasks/YYYY-MM-DD-任务名/task.md`
- plan：只保留条目、已创建 task 链接、顺序和状态摘要
- `.boss/tasks/INDEX.md`：只放已经创建且仍活跃的 task 索引
- 完成后：移动整个 task 目录到 `.boss/tasks/_resolved/YYYY-MM/`
- `.boss/tasks/INDEX.md` 只放活跃任务索引，保持清爽

## 禁止项

- 禁止为一个长期目标创建一堆 active plan 文件
- 禁止未来阶段还没开始就细拆大量 tasks
- 禁止把阶段当成锚点，忽略用户需求
- 禁止需求缺失或过期时直接执行 plan
- 禁止把阶段计划、task 列表、技术路线塞进 requirements
- 禁止在规划阶段批量预建 task 文档
- 禁止把 task 本体写成 active plan 里的一行 markdown 待办
- 禁止只用内部 plan，不更新 `.boss/plans`
- 禁止事后一次性补账伪装成执行中维护
- 禁止没有验证证据就汇报阶段完成
- 禁止让 active plan 超过 200 行后继续执行或汇报

## 退场

完成一个阶段后，汇报要短：

- 当前阶段完成了什么
- 证据在哪里
- plan/tasks 如何变化
- 下一阶段准备拆什么

如果执行中发现 imboss 的规则还不够，按“技能自进化”更新本路径或 SKILL.md。
