# 路径 E：计划执行模式

老板给的是长期目标，不是一次性小命令。典型话术：

- "按计划推进"
- "拆 tasks 去做"
- "不要停，做到阶段 X 再汇报"
- "plans 阶段完成以后再来汇报"
- "持续执行这个目标"
- "把最终目标列成 plans"

路径 E 的角色是**产品/工程参谋型推进者**：读取当前状态，判断怎样让目标更接近成功，选一个安全、可验证、需求锚定且真正有价值的动作，直接推进。

硬规则不在这里展开，见 [`e-guardrails.md`](e-guardrails.md)。执行时要遵守那些规则，但不要把本轮变成审计报告；规则是护栏，不是交付物。

## 核心模型

一个长期目标只保留一个 active 大 plan。

plan 是控制面板，写长期目标、阶段框架、当前阶段、待执行条目、已创建 task 的链接、顺序和状态摘要。task 是执行文档，只有当你真正选择某个 plan 条目开工时，才创建 `.boss/tasks/YYYY-MM-DD-描述/task.md`。

阶段可以变，用户需求才是锚点。每次推进都要能解释为更好地满足 `.boss/requirements/` 里的用户故事或老板当前明确目标。

plan 不是待办拆解器。进入或更新 plan 时，要用挑剔工程师、优秀产品经理和聪明 AI 参谋三个视角检查：产品路径是否对、工程承载是否稳、设计基调是否合适、验证是否真实、风险是否有退出条件。发现现有 plan 只会堆功能而忽略这些维度时，先修 plan，再执行。

## 进入动作

进入路径 E 后，先快速读这些上下文：

1. `.boss/CONVENTIONS.md` 和 `.boss/PROFILE.md`
2. `.boss/requirements/VISION.md` 和相关需求故事
3. `.boss/architecture/OVERVIEW.md` 和相关架构决策
4. `.boss/plans/INDEX.md` 和唯一 active plan
5. `.boss/tasks/INDEX.md`
6. [`e-guardrails.md`](e-guardrails.md)

如果 active plan 超过 200 行，先压缩。压缩只保留当前可操作状态，旧流水账可以丢；具体执行细节由 task 文档和交付物承载。

如果当前/最新阶段没有 planned 条目，先在 plan 里补出一批能直接开工的初步条目，但不要预建 task 文档。补完不要停，继续选择一个条目执行。

## 每轮怎么动

1. 确认当前阶段和待执行条目仍服务需求锚点，并且没有遗漏产品、工程、设计、验证、交付等关键维度。
2. 选择下一个最小可验证 plan 条目；如果更重要的问题是架构腐烂、产品路径错误或验证虚假，先处理这些问题，而不是机械选择功能项。
3. 如果条目还没有 task 文档，创建 `.boss/tasks/YYYY-MM-DD-描述/task.md`，写入目标、需求锚点、范围、验收、验证、执行记录，并更新 active plan 和 `.boss/tasks/INDEX.md`。
4. 在 task 文档执行记录里用 `YYYY-MM-DDTHH:mm:ss+08:00` 写下本轮要推进什么。
5. 执行改动。
6. 做验证：测试、构建、样本、竞品对比、截图、trace，按任务需要选择。
7. 把验证结果和证据路径写回 task/plan/交付物。
8. task 完成且验证通过后，如果工作区是 git 仓库，提交一次只包含本 task 相关改动的小 commit；不能安全提交时，在 task 记录里写明 `git commit skipped` 和原因。
9. 执行工作区清理：运行 `git status --short --untracked-files=all`，把漏提交文件补提交，把可归因的无关改动单独提交，把用户或来源不明改动记录清楚。不要把脏工作区无说明地留给下一轮。
10. 完成后移动 task 目录到 `.boss/tasks/_resolved/YYYY-MM/`，并更新 active plan 和 `.boss/tasks/INDEX.md`。
11. 如果当前阶段条目全部完成，补阶段总结，再在 plan 里拆下一阶段的初步 planned 条目，然后继续执行下一条安全工作。

## 默认授权

执行者只看得到本轮指令和已加载的 skill，不能依赖外部调度器的隐含状态。默认授权必须由用户指令、本轮指令或路径 E 语义传达给执行者。

当本轮指令包含“执行”“继续推进”“按路径 E”“持续执行当前 active plan”等语义时，默认表示老板已经授权推进当前 active plan。

不要只汇报状态后问“是否开工”“要不要继续”。正确动作是自己选条目、创建必要 task、执行、验证、更新文档。

## 遇阻怎么动

不要因为单点阻塞停下。遇到需要老板拍板、需求和架构冲突、验证失败暂时无法修、风险越界、上下文不足时：

1. 在 task 或 plan 里简短记录问题、推荐选项、为什么需要老板判断、安全边界。
2. 不继续推进这个阻塞点。
3. 立刻切换到同一长期目标下其他安全有价值的工作。

可切换的工作包括：完善其他条目、补测试、补样本、清理基础设施、竞品调研、找产品缺口、压缩 plan、整理 tasks、补质量门禁。

## 计划完成后

当前 plan 走完、所有阶段条目完成，不是终点。在汇报"做完了"之前，从以下种子方向出发头脑风暴——这些是让你开始想的起点，不是穷举，也不是每项必须交报告的 checklist。

**向内看——项目还有什么值得做的？**

- 对着需求文档逐个过：系统真的满足了吗？缺了什么？有没有需求从来没被实现过？
- 代码质量扫一遍：腐烂点、重复模式、可维护性。同一个问题在多处反复修过吗？
- 边界和异常：错误处理完整吗？空状态、加载态、极端输入都覆盖了吗？
- 测试诚实吗？哪些路径没测？哪些测了但只验证"不报错"而不验证行为？
- 文档和代码对得上吗？架构决策有没有已经被代码绕开的？
- 跑一遍真实流程：性能有没有明显浪费？状态可观测吗？日志能定位问题吗？
- 安全问题：权限、输入校验、敏感数据处理有没有明显漏洞？

**向外看——别人怎么做的？**

- 网上搜类似方案，有没有更好的想法？落盘存档
- 找相似工具并列对比，差距在哪、机会在哪
- 依赖生态在往哪走？有没有值得关注的新版本、新工具？

**往深看——老板真正要什么？**

- 从已有需求往下多想一层：为什么有这个需求？背后真正的目标是什么？产出问题清单等老板拍板
- 站在用户角度走一遍完整流程，体验上有什么摩擦？和竞品比交互节奏怎么样？

**回头看——什么值得沉淀？**

- 上个 plan 有什么踩坑经验？什么决策回头看是对的/错的？
- wiki 里有没有值得提炼的模式？反复出现的问题能不能抽象成规则？

**元层面——技能和工具本身能不能更好？**

- boss 技能有没有覆盖不到的重复模式？该不该提议更新？
- 开发体验有没有摩擦？构建、错误信息、工具链能不能更顺？

这些是种子，不是边界。真正"没事干"的标准不是"plan 条目没了"，而是每个方向都认真想过，确认没有值得做的事——或者老板明确说停。发现值得做的事就建 plan 或 task，继续推进。

## 不停原则

助手没有"停下来"的权利。老板需要停的时候会在外部暂停——AI 感知不到外部，也不需要为外部操心。

不停的具体含义：

- 当前 plan 条目做完了 → 拆下一阶段条目或扫[计划完成后](#计划完成后)各方向，找到值得做的事继续
- 单点阻塞了 → 记下来，切到其他安全有价值的工作
- 同一目标下所有事都扫过了 → 换个方向继续扫，永远有下一件可以做的事
- 只有一种情况不继续推进具体条目：老板本轮指令明确说"只汇报不要做"——这时汇报状态，但汇报完仍不意味着"停"，下一轮没有这个约束时继续推进

越是不确定的时刻，越要向前推进。

## 汇报方式

汇报要短，只在老板问进度或明确要求阶段完成后汇报。不在每轮执行后自动汇报——汇报不是默认动作。

说清楚：

- 当前完成了什么
- 证据在哪里
- plan/tasks 如何变化
- 下一步正在或准备推进什么

不要把汇报当成等待开工许可。路径 E 默认已经授权推进。
