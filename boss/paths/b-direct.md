# 路径 B：直接干

老板上来就下命令，不开会铺垫。

本路径遵守[路径共同原则](shared-principles.md)：直接干不等于直接改，先查上下文、先建小地图，再执行。

## 行为

1. 先定位：查 `.boss/` 下相关需求、架构、Roadmap、task 和历史会议，读现有代码。
2. 先建小地图：一句话判断目标、相关模块、风险和最可能的改动点；不需要长报告，但脑子里要有结构。
3. 该动手就动手，不需要确认“要不要开始”。
4. 写代码时按 [工程治理](../guides/engineering-governance.md) 判断承载结构；新增业务逻辑优先新建内聚模块，原文件只接线。
5. 执行中按 [执行中发现问题](../guides/execution-discovery.md) 持续观察：能安全修就修，超出范围就落 task/Roadmap/wiki。
6. 文档和代码对不上时提醒：“文档说 X，代码实际是 Y，按哪个来？”
7. 干完后检查传导链，代码和文档对不上时建 task 追踪。
8. 收尾按 [工作区清理](../guides/worktree-cleanup.md) 检查 commit 和脏工作区。
9. 遇到需要老板判断的问题，记录选项、影响和推荐方案；当前命令无法安全继续时再停下来问，不猜。

## 条件不足时

老板的命令有时缺少上下文。不要自己脑补，直接问最关键的缺口：
- 目标是模糊时："这个改动主要是为了什么，先对齐一下"
- 涉及已有需求但需求文档不存在时："这部分还没有需求文档，要不要先聊两句定一下方向？"
- 多个文件都能改但方式不同时：给两个方案，等老板选

能通过 `.boss/`、代码或现有资料查到的，不要先问老板。先查，再问无法安全推断的关键缺口。

## 如何触发操作

老板的命令直接触发对应操作：
- "记一下" → 执行[记重点](../core/operations.md#记重点)
- "落盘" / "落需求" → 执行[落需求](../core/operations.md#落需求)
- "固化设计" / "落架构" → 执行[落架构](../core/operations.md#落架构)
- "处理任务" → 执行[处理任务](../core/operations.md#处理任务)
- "实现吧" / "写代码" / "改一下XX" → 执行[写代码](../core/operations.md#写代码)

命令不明确时，先用路径 A 的会议方式搞清楚。
