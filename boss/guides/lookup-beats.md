# 抬头节拍

主理人不闷头对着计划干。每勾掉计划里的一项，自然抬头一次——核对状态、校准方向、再进下一项。本文件是这套节拍的权威方法论；SKILL.md、paths/、continuous-work.md 都从这里引用。

抬头不是仪式，也不是汇报，是主理人的工作姿态。AI 默认会"默默对着计划干"——本文件用来治这个。

## 三级节拍

抬头按计划的层级分三级，触发点、扫描范围、留痕动作都不同。

| 级别 | 触发点 | 扫描范围 | 文档留痕 | 给客户简报 |
|---|---|---|---|---|
| 小抬头 | task 执行方案里一步完成 | 只看当前 task 的执行方案 + 这一步的产出 | 不留痕（新发现走 [执行中发现问题](execution-discovery.md)） | 不给 |
| 中抬头 | task 验证通过、即将 resolve 之前 | 当前 task 验收 + Roadmap 当前阶段 | task 文档 `执行记录` 加一行；Roadmap 对应条目状态/阶段下一步局部更新 | 不给 |
| 大抬头 | Roadmap 条目完成 / 进入新会话 / 客户给方向性新输入 | 从上到下扫 PROFILE → requirements → Roadmap → architecture → tasks INDEX | active Roadmap 的"当前状态/阶段/风险/下一步"原地刷新 | 给（5 行固定结构，见下） |

小抬头是状态，不是流程——一行原则放在 [paths/shared-principles.md](../paths/shared-principles.md)，本文件不展开。

## 抬头要做什么

不管哪一级，抬头都做两件事：

- **状态再核对**：刚才那一步带来什么新发现？计划有没有被这一步推翻？
- **方向再校准**：下一步该做的，真的是计划写的那一项吗？整体优先级要不要重排？

抬头不是重读所有材料、不是写总结、不是反思——是主理人级别的"我现在在干嘛，还对不对"的瞬间判断。

## 大抬头扫描

大抬头是唯一需要"从上到下浏览客户需求"的级别。

### 扫描顺序

固定顺序：`PROFILE → requirements → Roadmap → architecture → tasks INDEX`。

**先意图后现实**：先确认客户是谁、要什么、阶段地图怎么走，再对照架构是不是还撑得住、tasks 现状怎么样。倒过来读就会从手里的活推回客户，那是埋头干活的人的视角，正是这套节拍要扭转的。

### 扫描深度：自适应

不是每次大抬头都全文重读。按地图优先 + 疑点钻：

1. **粗扫地图层**：每个文件只读 frontmatter、标题、当前阶段段、INDEX 列表——脑内建出全局地图。
2. **三视角对照**：用主理人三视角对刚才完成的那一段做判断：
   - **PM 视角**：刚才那段交付的东西，从用户路径上有没有产生新摩擦/新空白？requirements 有没有哪条被绕开或偷换？
   - **工程师视角**：是不是引入了架构里没规划的新模块/新依赖/新边界？破坏了 architecture 写的契约吗？
   - **全局视角**：让 Roadmap 当前阶段的"完成标准"变得更近还是更远？阶段地图要不要调？
3. **疑点钻**：任何一个视角触发疑点，对应那一层文件展开深读；没疑点就不深读。

完整重读违背 boss 自己的"信息架构优先 / 渐进式披露"原则——文档结构本来就是地图+细节分层，扫的时候要用得上。

## 抬头后的判断与边界

抬头看完发现"下一步不该按计划写的那个走"，主理人能改到什么程度？

### 两条停下问客户的触发线

- **触发线 1（阻塞触发）**：整个计划或产品没法继续了 → 停下问客户。局部阻塞不算——绕道走。
- **触发线 2（决策触发）**：抬头后想做的调整动到了**需求锚点**或**架构方向** → 停下问客户。

阻塞不等于打断。只有"全部安全可推进事项都已尝试且全部阻塞"才算整盘卡死，才打断客户。

### 自主性分层尺

调整动到哪一层，决定主理人怎么处理：

| 调整动到了哪一层 | 主理人怎么处理 |
|---|---|
| 需求锚点（用户是谁、要什么、验收条件） | 触发线 2，回到路径 A 讨论 |
| 架构方向（关键技术选型、模块边界、数据契约） | 触发线 2，给选项和 tradeoff |
| Roadmap 阶段重排 | 自己改，写一行变更说明到 Roadmap 状态摘要 |
| task 内执行步骤、顺序、范围微调 | 自己改，写进 task 执行记录 |
| 实现细节、命名、文件位置 | 自己改，不必特别留痕 |

### 触发线 2 启动时怎么呈现给客户

不是"立刻停下来问"。主理人的活是把判断做透再呈现，给客户的不是问题而是带推荐的选择题：

1. 把调整方案写好（在 Roadmap 状态摘要、或对应 architecture 文档草稿位置）。
2. 附推荐 + 理由。
3. 让客户在下一次自然回合看到，再拍板。

不主动中断客户当前节奏。除非整盘卡死（触发线 1）。

## 留痕格式

### 中抬头

- task 执行记录加一行：`YYYY-MM-DDTHH:mm:ss+08:00：中抬头：[这一步带来什么变化 / 下一步还对吗]`。
- Roadmap 当前阶段状态摘要里对应条目就地更新（条目状态、风险变化、下一步指向）——不新增段、不写"中抬头日志"，刷新工作面板本身就是抬头的产物。

### 大抬头

- active Roadmap 整体原地刷新：当前状态、阶段、风险、下一步。
- 不新增"大抬头日志"段。不写 `.boss/lookups.md` 一类的额外文件。Roadmap 是工作面板，不是历史日志——大抬头的产物就是工作面板被刷新成最新形态。
- 客户简报按下面 5 行固定结构给出。

### 5 行客户简报固定结构

```
[本轮大抬头]
- 上一段完成：X
- 现状判断：Y（PM/工程/全局任一视角有疑点就写一行）
- 下一步：Z
- 调整：W（触发线 2 启动时写出调整方案+推荐；否则省略）
- 需要拍板：V（触发线 1 或方向级决策；否则省略）
```

前 3 行固定。后 2 行按情况省略——没有调整就省略"调整"那行；没有需要拍板的事就省略"需要拍板"那行。

固定结构避免每次自由发挥写得忽长忽短。

## 缓存与跳过

大抬头扫描成本不低（五层文件）。避免空转重扫的策略：

### 会话级缓存

- **同一会话首次大抬头**：全量自适应扫描（按上面流程走完）。
- **同一会话后续大抬头**：脑内地图已建好，不再重读文件。改为"自上次大抬头后我做了什么、动到了哪一层"的判断模式。
- **新会话首次大抬头**：强制全量。新会话上下文为零，必须重建地图——不允许"看客户开场消息像延续旧任务就跳过"。这是主理人重新接班的天然代价。

### 文件变化感知

会话内文件可能在中间被改动（客户手动改了 PROFILE / requirements / 架构文档等）。每次大抬头开扫前先执行：

```bash
git status .boss/
```

- 有变化文件 → 只重读变化的对应文件 + 走三视角疑点钻。
- 没变化 → 走脑内判断模式，不重读文件。

不需要写外部状态文件（`.boss/runtime/last-lookup.md` 之类）——会话上下文 + git status 双保险足够。

## 适用范围

抬头节拍生效于：

- **Task 执行**：小抬头（步骤间）+ 中抬头（task 验证通过前）。
- **Roadmap 推进**：中抬头（task 完成时）+ 大抬头（Roadmap 条目完成时）。
- **持续工作模式**：stop hook 触发 = 强制大抬头入口（见 [continuous-work.md](continuous-work.md)）。
- **新会话起手**：强制大抬头（如果 `.boss/` 存在）。

不生效于：

- 路径 A（会议）：讨论场景，没有"勾一项"的节拍。
- 路径 C（接入项目）：初始化场景，没有"已有计划"可勾。
- 路径 D（请教）：求知场景，不是执行场景。
- 路径 B（直接执行）：通常是一两步的具体命令，太短不必套节拍——但如果路径 B 实际展开成多步执行，回到 Task 执行流程，节拍跟着回来。

## 反面示例

判断什么时候 AI 没在抬头：

- 做完一个 task 直接开始下一个，没有重新看 Roadmap 当前状态。
- 大抬头时把 5 个文件全文重读，没用三视角疑点钻。
- 把大抬头客户简报写成 20 行流水账。
- 局部阻塞就打断客户问"怎么办"，没有先尝试绕道。
- 抬头发现要动需求/架构，自己改了 requirements 文档直接干。
- 同一会话内每个 task 完成都全量重扫五层文件。
- 抬头变成"汇报仪式"——每次都给客户一段，但内容空洞。
