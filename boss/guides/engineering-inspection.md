# 工程巡检方法论

本文件给执行 AI 看。

"看得更多"给出的是方向——但方向不是操作方法。AI 对着"向内看"卡住，是因为不知道该读哪个文件、怎么对比、怎么判断、产出什么。

本文件给每个巡检方向配上具体操作方法：读什么、比什么、怎么判、产出什么格式。

巡检的核心心法：**先产出发现清单，再挑一个执行**。不要巡到一半觉得"这个可以修"就直接动手——把发现记下来，巡完一个方向再排优先级。

## 巡检操作说明

每个巡检条目 = 目标 + 操作步骤 + 判断标准 + 产出格式。

操作步骤告诉 AI"具体读哪个文件、对比什么、用什么工具"。
判断标准告诉 AI"什么算问题、什么不算"。
产出格式告诉 AI"发现之后怎么记、记在哪里"。

## 1. 架构-代码对齐

**目标**：找出架构文档和实际代码之间的偏差——文档里写了但代码里没有、代码里有但文档没覆盖、模块边界被违反。

**操作步骤**：

1. 读 `.boss/architecture/OVERVIEW.md` 和每个架构文档的结构图部分，把模块列表摘出来。
2. 对每个模块，找到它在代码里对应的目录/文件。不确定时 `ls` 看目录结构、`grep` 关键类名/函数名定位。
3. 对比检查：
   - 文档里的每个模块 → 代码里有对应物吗？没有 → 记录为"文档有、代码无"。
   - 代码里的每个顶层目录/包 → 文档里有对应条目吗？没有 → 记录为"代码有、文档无（可能遗漏的模块）"。
   - 两个模块之间是否有导入关系被架构文档明确禁止？有 → 记录为"边界违反"。
4. 读架构文档里标注为"几乎不变"的组件，检查代码里是否真的稳定——最近 git log 是否频繁改动、是否被多处引用修改。

**判断标准**：
- 文档有代码无：要看是还没实现（需建 task）还是文档过时（需更新文档）。
- 代码有文档无：可能是遗漏模块，也可能是不值得入架构的临时目录——前者补文档，后者不用处理。
- 边界违反：架构约束被绕开，需要讨论是架构该改还是代码该修。

**产出**：按"模块 → 偏差类型 → 严重程度 → 建议动作"记录到当前 task 或新建 discovery note。格式：

```
## 架构-代码对齐发现

### 模块 XXX
- **偏差**：文档描述 XXX，但代码中 YYY
- **严重**：高/中/低
- **建议**：更新文档 / 修复代码 / 创建 task
```

**优先级判断**：架构文档标注为"几乎不变"的组件出现偏差 → 高优先。临时目录没文档 → 低优先。

## 2. 模块深度巡检

**目标**：逐个模块深度审视——功能是否完整、边界条件是否覆盖、错误处理是否到位、有没有显而易见的 bug。

**操作步骤**：

1. 从 OVERVIEW.md 或代码顶层目录中选一个模块作为当前巡检目标。
2. 读该模块的所有源文件（先 `ls` 列文件清单，再逐个读）。
3. 对每个文件，检查：
   - 函数/方法的参数有没有做空值保护？边界输入（空数组、null、超长字符串）会不会崩？
   - 异步操作用了 error 处理吗？try-catch / .catch / Promise.allSettled 覆盖了吗？
   - 有没有 TODO、FIXME、HACK 标记？这些是明面上的技术债。
   - 有没有硬编码的魔法数字、URL、密钥？（密钥在代码里是高危）
   - 导出接口和实际使用对得上吗？有没有导出了但没人用的函数？
4. 用 git log 看该模块最近的改动历史——是不是频繁修 bug？同一个文件反复改可能说明设计有问题。
5. 如果有对应需求文档，对照需求检查：需求说的功能代码里都实现了吗？有没有需求里写了但代码里找不到的？

**判断标准**：
- 空值/边界没保护：功能 bug，中高优先。
- 缺少错误处理：可能导致静默失败，中优先。
- TODO/FIXME：看内容判断——TODO 里写了"临时方案，上线前改"但已经上线了 → 高优先。
- 硬编码密钥：高危，立即报告。
- 导出未使用：代码腐化信号，低优先。

**产出**：按"文件 → 问题 → 严重程度 → 建议修复方向"记录。

## 3. 模式一致性审计

**目标**：找出同一个横切关注点在不同模块里用了不同模式的情况——不一致本身就是技术债。

**操作步骤**：

1. 选一个横切关注点开始审计。常见的审计目标：
   - **错误处理**：try-catch vs .catch() vs callback err vs 不处理
   - **日志/上报**：console.log vs 结构化日志 vs 无日志
   - **HTTP 请求**：fetch vs axios vs 自定义封装 vs 裸调
   - **状态管理**：useState vs useReducer vs Redux vs 全局变量
   - **配置/常量**：硬编码 vs .env vs 配置文件 vs 远程配置
   - **类型使用**：严格类型 vs any vs 类型断言 vs 不写类型
   - **文件命名**：camelCase vs kebab-case vs PascalCase vs 混用
2. 对选定的关注点，grep 关键模式串遍历所有模块。例如查错误处理就 grep `catch`、`.catch(`、`err`、`error`、`throw`、`reject`。
3. 把找到的模式归类：模块 A 用方式 X，模块 B 用方式 Y，模块 C 什么都没用。
4. 判断哪个模式更好。判断依据：
   - 覆盖面：哪种模式覆盖了更多边界情况？
   - 可读性：哪种模式让调用方更容易理解？
   - 可维护性：哪种模式改动时影响面更小？
   - 社区实践：哪种模式是这个技术栈的主流做法？
5. 给出推荐模式，附一句话理由。

**判断标准**：
- 同一个 repo 里同一个事情有三种以上做法 → 必须收敛，中优先。
- 有一种做法明显比其他差（如硬编码 vs 配置化）→ 高优先。
- 主流模块用一种模式、孤立模块用另一种 → 孤立模块向主流对齐，低优先。

**产出**：按"关注点 → 现有模式分布 → 推荐模式 → 不一致模块列表 → 迁移难度"记录。格式：

```
## 模式一致性：错误处理

### 现状分布
- try-catch + 结构化日志：模块 A、B（3 处）
- .catch() + console.error：模块 C（5 处）
- 无处理：模块 D、E（7 处）

### 推荐
try-catch + 结构化日志 —— 覆盖面最好，已有两个主要模块在用。

### 不一致项
- [ ] 模块 C：.catch() → try-catch（低难度，5 处）
- [ ] 模块 D：补充错误处理（中难度，7 处）
```

## 4. 工程质量硬指标

**目标**：跑机器可检查的硬指标——这些不需要主观判断，有明确的"好/坏"分界线。

**操作步骤**：

1. **TypeScript 严格度**（如果是 TS 项目）：读 `tsconfig.json`，检查 `strict`、`noUncheckedIndexedAccess`、`noImplicitReturns`、`noFallthroughCasesInSwitch`、`exactOptionalPropertyTypes`。和社区最佳实践对比。
2. **文件体积**：统计每个源文件行数（`wc -l`），标出超过 500 行的。读这些大文件的头部和 import 区域，判断是否承担了多类职责。
3. **循环依赖**：如果项目有 `madge` 或类似工具就跑，没有就肉眼检查 import 关系——A import B、B import A 或更长的环。
4. **死代码检测**：grep 每个 export 的名字，看是否有 import 引用。没有被引用的导出标记为疑似死代码。
5. **配置文件卫生**：读 `package.json`——有没有 `dependencies` 和 `devDependencies` 混淆（如 `eslint` 在 dependencies 里）？有没有未使用的依赖？
6. **构建产物检查**：`.gitignore` 是否覆盖了 `node_modules`、`dist`、`.next`、`build` 等？实际目录里有没有不该提交的构建产物？

**判断标准**：
- tsconfig strict: false → 中优先（改起来动静大但收益高）
- 单文件 >500 行 → 中优先，>1000 行 → 高优先
- 循环依赖 → 高优先
- 死代码 → 低优先（可以批量清理）
- 依赖配置错误 → 中优先

**产出**：按"指标 → 当前值 → 建议值 → 严重程度"记录。

## 5. 模式提炼入库

**目标**：从代码中识别出不显而易见的模式，提炼成可复用的知识写入 wiki。这和"模式一致性审计"相反——前者找不一致，这个找一致但隐性的好模式。

**操作步骤**：

1. 通读代码时留意这些信号：
   - 同一段逻辑在 3 个以上不相关的地方出现但每次写法略有不同。
   - 某个模块的设计明显比其他模块"清爽"，但说不上来为什么。
   - 某个问题被反复踩坑（看 git log 里多次修同类 bug）。
   - 某个数据结构或接口设计让后续改动变得特别容易。
2. 对疑似模式，追查所有使用点，抽象出：
   - **模式名**：一个能望文生义的名字。
   - **它解决了什么问题**：动机一句话。
   - **结构**：核心组件和它们的协作关系。
   - **适用场景**：什么时候用、什么时候不用。
   - **示例**：从当前代码里取一个最小可读片段。
3. 写入 `.boss/wiki/patterns/模式名.md`。如果 wiki 目录不存在，先建 `wiki/` 和 `wiki/patterns/`。
4. 在 CONVENTIONS.md 的 pattern 相关条目下加一句回链。

**判断标准**：
- 有参考价值：3 个以上使用点，或解决了一个反复出现的问题 → 值得入库。
- 一次性巧合：只出现一次，且没有明显通用性 → 不值得入库。

**产出**：`wiki/patterns/` 下的模式文档 + CONVENTIONS.md 回链。

## 6. 文档完整性

**目标**：确保 `.boss/` 下的文档和代码/事实一致，不积累信息偏差。

**操作步骤**：

1. 先扫 `.boss/` 目录结构，确认所有必需目录都在（CONVENTIONS.md、PROFILE.md、requirements/、architecture/、meetings/、roadmaps/、tasks/、wiki/）。
2. 读 CONVENTIONS.md，对照实际代码检查：
   - 约定的命名规范代码里在遵守吗？
   - 约定的目录结构实际在用吗？
   - 约定的工作流还在执行吗？
3. 读 PROFILE.md，检查是否仍然反映老板的当前偏好。
4. 对照 git log 最近 20 条 commit，检查：
   - 有没有完成但没有对应 task 文档的工作？
   - 有没有改了代码但没更新架构文档的情况？
5. 检查 requirements/ 和 architecture/ 之间的引用关系——有没有需求引用了不存在的架构决策？有没有架构文档引用了已过期的需求？
6. 检查 INDEX.md 文件——`.boss/tasks/INDEX.md` 和 `.boss/roadmaps/INDEX.md` 是否和实际目录内容一致？有没有漏登或已归档但没删除的条目？

**判断标准**：
- CONVENTIONS 和代码不一致 → 要么更新规范要么修代码，中优先
- 缺 INDEX 条目 → 低优先但应该立刻补
- 引用断裂 → 高优先

**产出**：按"文档 → 问题 → 建议动作"记录。

## 巡检执行规则

**什么时候巡检**：当前 task 或 Roadmap 条目完成且无直接可推进项时，从巡检目录里选一个方向开始，不要直接停。

**怎么选方向**：
1. 上次巡检是什么方向？换一个没巡过的。
2. 距上次巡检超过 5 轮 → 可以复巡同一方向（代码可能已经变了）。
3. 如果某个方向之前产出过发现但还没处理完 → 先处理已有发现，不重复巡。

**怎么巡**：
1. 选方向 → 按操作步骤执行 → 产出发现清单。
2. 发现清单里如果有低成本的修项（改一行配置、补一个文档条目、删一段死代码）→ 顺手修了再记录。
3. 发现清单里需要设计的 → 建 task 或追加到 Roadmap planned。
4. 发现清单里需要老板拍板的 → 记下来，切回路径 A 讨论。

**不要做的事**：
- 不要在巡检过程中直接重构代码。巡检是侦查，不是改造。
- 不要产出一份没有优先级的平铺清单。每条发现必须有严重程度和理由。
- 不要只写"没发现问题"。如果真没发现，写清楚"巡检了 X 方向，读了 Y 文件，用了 Z 判断标准，没发现不符合"——让你的巡检过程可被审计。

**巡检不是一次性项目**。它是持续工作模式空转时的默认动作——每次空转都巡一个方向，发现清单像雪球一样滚大，越巡越有东西可做。
