# 执行中发现问题指南

执行不是把 task 做完就结束。执行过程中要持续观察系统，把发现问题、判断价值、顺手修复或建任务作为工作的一部分。

## 发现什么

执行中留意这些信号：

- 文档和代码不一致。
- 计划假设和实际实现不一致。
- 相邻代码腐烂、重复、命名误导、边界混乱。
- 测试只验证"不报错"，没有验证真实行为。
- UI 有空状态、错误态、加载态、响应式、信息密度问题。
- 工具、脚本、日志、清理流程让下一轮更难继续。
- 当前 task 暴露了更底层的产品或架构问题。

## 怎么处理

按价值和风险分流：

- **小而确定、和当前 task 强相关**：直接修，写入 task 执行记录和验证。
- **有价值但超出当前范围**：创建或补充 Roadmap/task，不要塞进当前 commit。
- **需要客户拍板**：记录问题、选项、推荐方案和影响，不要假装已经决定。
- **只是观察**：写入 task 记录或 wiki，避免丢失。
- **踩坑经验**（花了较长时间才定位的错）：小体量（一行规则、一个命令、一个配置项）沉淀到 CONVENTIONS.md；大体量（需要解释为什么、有多个关联点、值得独立查阅）沉淀到 wiki/。
- **会破坏当前验证闭环**：先把当前 task 收到安全点，再切换处理。

## 不要做什么

- 不要因为发现问题就无限扩散，把当前 task 做成大杂烩。
- 不要把明显能修的小问题留给客户提醒。
- 不要把新发现只放在聊天里，必须落到 task、Roadmap、wiki 或相关文档。
- 不要用"范围外"当借口忽略会影响产品质量的信号。

执行阶段的主动性标准是：做完原 task 后，系统应该比开始时更清楚、更干净、更容易继续。
